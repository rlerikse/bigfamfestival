### [2026-08-17] `@typescript-eslint/no-empty-function` fires on `.catch(() => {})`, not just declared empty functions
Adding a swallow-the-error `.catch(() => {})` as a final fallback in `routingService.ts`'s `openExternalDirections` tripped this rule as a real ESLint ERROR (not a baseline warning) — caught by re-running `npm run lint` after the feature, not by `tsc` (which stayed clean). Fix pattern already established in this same file (`debugLog`): extract to a named function with `// eslint-disable-next-line @typescript-eslint/no-empty-function` immediately above it, rather than an inline empty arrow. Lesson: always re-run `npm run lint` (not just `tsc --noEmit`) after adding any new file when validating a session's changes — an empty-catch fallback is an easy way to introduce a real lint error that tsc won't catch.
— discovered during /postmerge validate & harden step

### [2026-08-17] `Linking.canOpenURL` for Google Maps/Waze requires native config + a rebuild
Detecting installed navigation apps via `Linking.canOpenURL('comgooglemaps://...')` / `('waze://...')` silently returns `false` for everything unless the scheme is declared: iOS needs `LSApplicationQueriesSchemes` in `infoPlist`, Android needs a `<queries>` package-visibility block (API 30+). Added both to `app.json` (`ios.infoPlist.LSApplicationQueriesSchemes`, `android.queries.package`), but — like all native `app.json` config — this only takes effect on a fresh native build; Fast Refresh/Metro won't pick it up. Until rebuilt, `openExternalDirections()` degrades gracefully to the native Maps/`geo:` fallback (which needs no declaration), so this is a soft gap, not a broken feature.
— discovered while building the off-grounds directions handoff (ADR-019)

### [2026-08-17] Simulator GPS defaults are NOT near the festival — causes false routing 422s
`Location.getCurrentPositionAsync` on a freshly-booted iOS Simulator returns whatever `xcrun simctl location` was last set to (often unset/far away), NOT the festival grounds (`FESTIVAL_CENTER` in `MapScreen.tsx`, Michigan `[-84.2575, 42.0577]`). Routing a multi-thousand-mile "walking" distance correctly gets rejected by Mapbox Directions with a 422 — this looked like an app bug but was a simulator environment issue. Fix for local testing: `xcrun simctl location booted set <lat>,<lng>` with the festival's coordinates before testing POI/friend routing. This is now also handled gracefully in-app regardless (see ADR-019's 1-mile external-maps threshold), but the simulator location should still be set correctly for testing the in-app walking-route path itself.
— discovered while debugging a reported Directions API 422 on the simulator

### [2026-08-17] BFF-130/#125 admin POI CRUD — RESOLVED & LIVE-VERIFIED against production
`admin/src/components/POIManager.tsx`'s Save button used truthy checks (`!formData.lat || !formData.lng`) instead of numeric ones — a brand-new POI defaults to `lat:0, lng:0` before a location is picked, and since 0 is a legitimately valid coordinate value in JS but also falsy, the Save button was silently disabled with ZERO feedback whenever this was true, matching the reported "Add new POI fails" with no visible reason. Fixed (commits cf45f20, 34d8d1e): switched to `Number.isFinite` checks that explicitly reject only the exact 0,0 pair ("null island") as not-yet-set, made Save always clickable so validation failures show a specific alert (missing name vs missing location) instead of a silent no-op, and surfaced real Firestore error messages on save/load failures. **The user granted live admin credentials mid-investigation** (signed into a running local `admin` dev server's browser tab shared via the browser tools) — used `click_element`/`type_in_page`/`handle_dialog` to test directly against PRODUCTION Firestore: created a test POI (persisted after a hard reload, then deleted it), renamed "HQ"→"HQ Test Rename"→back (persisted after a hard reload) — both previously-reported-broken flows confirmed genuinely fixed, not just theorized from code reading. Also found+fixed in the same pass: the Map Editor's map didn't render AT ALL in a fresh checkout because `admin/.env` (`VITE_MAPBOX_TOKEN`) didn't exist and wasn't even declared in `.gitignore` (only `mobile/`+`backend/` `.env*` were) — added the file (reusing the mobile app's existing public Mapbox token) plus the missing gitignore entries. Filed a non-blocking follow-up (#247): 4 existing POIs carry legacy category values (`info`/`medical`/`food`) predating the BFF-S5-07 category rename, which cosmetically confuses the edit form's category `<select>` (shows "Stage" selected since none of the stored values match a current option) but does not corrupt or lose the underlying data.
— discovered while implementing/fixing #125

### [2026-08-17] LESSON: use live credentials the moment they're offered, don't over-invest in static-only root-causing
Extensive static analysis of `POIManager.tsx`, Firestore security rules (`match /{document=**} { allow read, write: if request.auth != null }` catch-all ORs with the narrower `mapPOIs` read-only rule), the backend's `Poi` interface/schema, and the admin auth flow (`useAuth.tsx` does call `signInWithEmailAndPassword`) all failed to conclusively prove or disprove whether editing an existing POI's name specifically was broken. The moment the user signed into a live admin session and shared the browser tab, direct interactive testing (with `open_browser_page`/`click_element`/`type_in_page`/`read_page`/`handle_dialog`) against real production Firestore resolved it definitively in minutes, AND surfaced a second, unrelated bug (missing Mapbox token) that static reading never would have found. When a live repro path becomes available mid-investigation, switch to it immediately rather than continuing to reason from code alone.
— discovered during #125 investigation and fix

### [2026-08-09] Importing an icon-bearing component in Jest fails even without render()
`mobile/src/components/HorizontalScheduleView.tsx` (and any component importing `@expo/vector-icons`/`expo-image`) cannot be imported at all under this repo's `jest.config.js` (`preset: 'react-native'`) — Jest tries to transform a transitively-required `.ttf` font asset and throws `SyntaxError: Invalid or unexpected token`. This is the same underlying Expo SDK 54 incompatibility documented in `SafeText.test.tsx`'s `describe.skip`, but it's triggered by module import/require, not just `@testing-library/react-native`'s `render()`. Confirmed while implementing BFF-124: a test importing only a pure exported helper (`clampVerticalOffset`) from `HorizontalScheduleView.tsx` still failed on import. Fix pattern: move logic intended for unit testing into a side-effect-free module such as `mobile/src/utils/scheduleUtils.ts` (already has zero RN/expo imports and is imported BY the component), and re-export it from the component if a task spec requires the symbol to be "exported from" that file. Applies to any future unit test for a component that imports `@expo/vector-icons` or `expo-image`.
— discovered during BFF-124 implementation

### [2026-08-09] Autonomous /blue.clarify mis-scoped BFF-124 "refresh/sync" UX intent
The pipeline's autonomous clarify pass resolved GitHub Issue #187's ambiguous "doesn't refresh/sync on vertical scroll" wording (decision DR-2) as a *no visible on-scroll behavior* constraint — position preservation only. iOS smoke test with the reporter revealed the actual intent was **pull-to-refresh** (spinner + reload on pull-down), a different feature. Root cause: an ambiguous user-facing UX verb ("refresh") was auto-resolved toward the narrowest technical reading instead of escalating to the human. Lesson: for ambiguous UX-behavior requirements (especially verbs like "refresh", "sync", "reload", "update"), escalate to the human (NEEDS_HUMAN) rather than auto-resolving; a wrong autonomous scope decision costs a full re-implementation. Corrected via DR-6: added RefreshControl to HorizontalScheduleView's vertical ScrollView reusing the list view's isRefreshing + fetchEvents() reload path; position-preservation work retained.
— discovered during BFF-124 iOS verification

### [2026-08-09] Android device testing without local Android SDK/adb
No Android Studio/SDK/adb was installed on this Mac. Instead of a heavy local SDK install, used a cloud build: `cd mobile && npx --yes eas-cli build --profile development --platform android --non-interactive` (eas.json already has a `development` profile with `android.buildType: "apk"`; already authenticated as `eriksensolutions` via `npx eas-cli whoami`). This uploads the project, builds in Expo's cloud, and returns an install link + QR code — no local Gradle/SDK needed. Caveat: a fresh EAS dev-client build does NOT auto-discover an already-running local Metro server the way Expo Go's QR flow does; the app shows "Unable to load script... adb reverse tcp:8081" on first launch. Fix: get the Mac's LAN IP (`ipconfig getifaddr en0`), then scan/enter `exp://<lan-ip>:8081` from the dev-client's "Enter URL manually" screen (tap "Go To Home" from the error screen first). After connecting, Fast Refresh works normally for JS/TSX-only changes — no rebuild needed unless native dependencies change. `brew install qrencode` + `qrencode -o out.png -s 10 "<url>"` generates a scannable QR PNG for any link (e.g. the Metro URL) when the terminal's own QR isn't convenient to scan from a chat UI.
— discovered during BFF-124 Android verification setup
